## 1. Что хотим
- Два входа в **один аккаунт**: Telegram-бот и сайт (email + пароль); сайт работает и как Telegram Mini App.
- Бот присылает напоминания и статистику; та же статистика и графики — в кабинете на сайте.
- Квартиры и счётчики с выбором модели; ввод показаний по пошаговому алгоритму модели; мастер новой модели.
- Показания **для отправки** (одно за период) и **промежуточные** (статистика, в т.ч. M-Bus).
- Отправка в ХТМ под логином пользователя **в фоне**: пользователь нажимает «Отправить» (или срабатывает расписание), сервис сам входит в кабинет ХТМ, заполняет поля, отправляет и проверяет; пользователь получает только подтверждение «принято ХТМ» с доказательством.
- Режимы: вручную, сразу после сбора, в выбранный день (по умолчанию **20-го**, в окне 5–25 с запасом до рекомендованного 23-го).
- Логин и пароль от кабинета ХТМ хранятся в сервисе; владелец может посмотреть их на сайте или получить в боте.
- Напоминания, справочник ошибок, учёт повирки, платёжки, новости.
- Бесплатное ядро + подписка.
- Тестовый стенд, повторяющий кабинет ХТМ 1:1.

## 3. Точки входа и аккаунт
> Реализовано 01.11.2026 (репозиторий teplo_test, `design/07-sync-auth-photo.md`): вход из бота сам (Mini App, `initData`), на сайте — Telegram Login Widget или email+пароль, один аккаунт, данные на всех устройствах (сначала локально + синхронизация), защита — Cloudflare Tunnel + лимиты/блокировки/CSRF в приложении.

Одно PHP-приложение, один аккаунт, несколько способов входа (`user_identities`):
- **Сайт**: email + пароль; опционально «Войти через Telegram».
- **Mini App**: те же страницы; вход по `initData` (HMAC).
- **Бот**: команды и кнопки через тот же сервисный слой.
Связка: сайт → deep-link `t.me/<bot>?start=<token>`; бот → аккаунт по Telegram, email/пароль позже.

Бот: `/start` (оферта и политика), `/reading`, `/send`, `/stats`, `/bill`, `/htm`, `/error <код>`, `/povirka`, `/news`, `/settings`, `/privacy`, `/paysupport`, «Открыть кабинет». Напоминания с кнопками «Ввести показания», «Напомнить завтра», «Отправить сейчас»; «Нет отопления».

## 4. Компоненты
```
Telegram (бот, Mini App) ─┐
Браузер (сайт) ───────────┼─► PHP-приложение (Web Station) ─► MariaDB
M-Bus-шлюз (опция) ───────┘   (/api/ingest)
                                   │
                   cli/cron.php (Планировщик DSM, каждые 5 мин) → jobs
                                   ├─ напоминания (окна, повирка)
                                   ├─ отправки → ProviderAdapter → ХТМ / стенд
                                   ├─ канарейка (изменился ли сайт ХТМ)
                                   ├─ новости, погода, подписки
                                   └─ уведомления (Telegram, email)
```
- `ProviderAdapter`: `login`, `listMeters`, `submitReading(dryRun)`, `verify`. `HtmAdapter` — cURL + cookie jar + DOM/XPath; `base_url` → боевой ХТМ или стенд. Если кабинет требует JS — headless Chromium (Playwright) в Docker на NAS.
- **Фоновая отправка:** пользователь нажал «Отправить» → задача в очередь → адаптер: вход → форма → заполнение → отправка → проверка в истории/подтверждении → уведомление «✅ Принято ХТМ» + доказательство. Пользователь ничего не видит, кроме результата.
- **Запасной режим (если автоматика не смогла):** сразу сообщение «не получилось автоматически» + ссылка на кабинет ХТМ + готовые цифры и пошаговая инструкция; повторы до конца окна. Капчу не обходим; появилась капча или изменилась разметка → канарейка ставит автоотправку на паузу для всех.
- Подачу через бота ХТМ от имени пользователя (userbot с его Telegram-сессией) **не делаем**.

## 5. Доступ к кабинету ХТМ: хранение и показ
- Хранится режим входа, логин (email или лицевой счёт), пароль (или фамилия) — обратимое шифрование (libsodium/AES-GCM), ключ вне веб-корня.
- При подключении спрашиваем, зарегистрирован ли пользователь в кабинете ХТМ (тогда вход только по email + паролю). Ошибку входа «счёт + фамилия» распознаём отдельно и предлагаем перейти на email + пароль.
- **Сайт:** логин виден, пароль по кнопке «Показать» после свежего входа; **бот** `/htm` — под спойлером, самоудаление через 2 минуты.
- Видит только владелец; каждый показ — в `audit_log`. Кнопки «Изменить», «Проверить вход», «Удалить доступ».

## 6. Показания и отправка
**Виды:** `intermediate` и `billing`. **Что снимаем:** энергия (обязательно), объём, расход, мощность, подача/обратка, часы On, Eh, код ошибки, примечание. Единица — у конкретного счётчика.
**Источники:** сайт, бот, импорт журнала, ссылка для арендатора/соседа, M-Bus.

**Окно — параметр поставщика и вида услуги** (`provider_windows`): ХТМ тепло **5–25** (рекомендовано до 23-го, снято с сайта 01.11.2026); ГВ в кабинете ХТМ не принимается — только через бот ХТМ (у нас — напоминание). Было: тепло 23–26; ХТМ ГВ — до предпоследнего рабочего дня (онлайн). Тепло и ГВ отправляем одним заходом в окно тепла.

| Режим | Как работает |
|---|---|
| `manual` | Собрал → проверил → «Отправить» → фон → подтверждение. |
| `after_collect` | Billing-показание, снятое в окне, после проверок уходит сразу (предупреждения → сначала спросить). |
| `on_day` | 20-го (по умолчанию; окно 5–25, рекомендовано до 23-го) уходит свежее показание (снято и передано в один день — иначе робот отклонит по часам). Нет свежего → напоминание и переход в `after_collect`; повторы до 25-го. |

- Только в отопительный сезон (вне сезона — вручную).
- Перед отправкой: проверки (документ «проверка показаний») + «уже передано?». После: `verify` + доказательство (HTML/скрин).
- Если форма ХТМ принимает часы с ошибкой — передавать Eh вместе с энергией.

**Напоминания (по умолчанию, окно 5–25):** 5-го «окно открыто», 18-го «снимите показания до 23-го», 22-го «завтра рекомендованный срок», 25-го «сегодня последний день», с 26-го — «окно закрыто, следующее 5-го» (если не отправлено). Каждое: «снимайте и передавайте в один день». При M-Bus — «снято автоматически, отправляю / отправить?». ГВ — отдельное напоминание «передайте показания ГВ в бот ХТМ».

**Подтверждение «принято ХТМ» с доказательством — бесплатно для всех** (рекомендация анализа аналогов: главная претензия к неофициальным приложениям — нет подтверждения подачи).

## 7. M-Bus (опция для энтузиастов, не основа бизнеса)
Sharky 774 пользователя имеет M-Bus (2 провода, полярность не важна, 300/2400 бод). Мастер шины: Raspberry Pi Zero 2 W + M-Bus Master Hat; libmbus → `POST /api/ingest`. Опрос ≤ 1 раза в час (ошибка E-5). Пломбы не трогать. Харьковская M-Bus-сеть OTOS свёрнута («зараз ця послуга не надається») — готовое железо продавать не торопимся.

## 8. Проверки, статистика, платёжки, ошибки, повирка, новости
- Проверки при вводе — «проверка показаний при вводе».
- Статистика: Гкал и стоимость по месяцам, сезон к сезону, среднесуточный расход, температуры/ΔT/мощность, градусо-сутки (Open-Meteo), прогноз суммы, сверка с платёжкой, аномалии.
- Платёжки: фото/PDF, ручной ввод строк (MVP), сверка, «обучение» доле МЗК+ФС на м².
- Ошибки и повирка — «ошибки и повирка». Новости — «новости».
- Мастер новой модели: фото экранов по нажатиям + шильдик → черновик → проверка админом.

## 11. Безопасность и данные
- password_hash для сервиса; обратимое шифрование доступа ХТМ; секретов нет в логах и трассах.
- Telegram: проверка подписи initData / Login Widget; webhook с секретом.
- Платёжки, фото, свидетельства — вне веб-корня, только владельцу.
- Нагрузка на ХТМ: один вход на отправку, без параллельных сессий, паузы между пользователями.

## 15. Бэклог идей
- Публичная страница «Когда и как передавать показания ХТМ» со ссылками на пункты договоров — закрывает реальный пробел (сроков не находят даже СМИ), канал привлечения.
- Предложить ХТМ партнёрство (официальный канал/API) **до** обновления их сайта: аргумент — сервис уменьшает начисления «по среднему».
- **Распознавание показаний по фото прямо на сайте (клиентская сторона).** Пользователь фотографирует табло счётчика (и, по желанию, шильдик) в мастере ввода — браузер **на устройстве** распознаёт и заполняет поля формы показаний ещё до отправки в ХТМ:
  - **Цифры с табло → показания.** OCR числа с экрана → в `energy_raw` (и, если на кадре видно, `volume_m3`, `flow_m3h`, `power_kw`, `t_supply`/`t_return`, `hours_on`/`hours_err`, `error_code`). Единицу берём не с картинки (у части моделей символ не показывается — Apator ELF), а из `meters.energy_unit`; разделитель/точность нормализуем под поле.
  - **Распознавание модели счётчика.** По шильдику (вендор/модель текстом) и по характерному виду табло определяем `meter_model_id` из каталога (Sharky 774, L+G T330/T230, Kamstrup, Apator, НІК 7071, TRUST…). Нашли — подставляем шаги снятия (`read_steps`) и единицу; не нашли/низкая уверенность — не угадываем, предлагаем выбрать модель вручную и уводим в **мастер новой модели** (фото экранов по нажатиям + шильдик → `meter_model_drafts` → проверка админом).
  - **Заполнение полей сервиса, не ХТМ.** Распознанное попадает в поля формы **нашего** сервиса (мастер ввода), помечается `source='photo'`, фото кладётся в `readings.photo_path` (вне веб-корня). Дальше — обычная проверка при вводе (светофор: ошибка / примет ли ХТМ) и только потом фоновая отправка. Автоматического заполнения полей на боевом сайте ХТМ по фото не делаем — туда уходит уже проверенное значение через адаптер.
  - **Приватность и режим работы (решение 01.11.2026, `design/07`).** Распознаёт vision-модель: в прототипе — Claude через возможность страницы (с согласием человека), на сервере — vision-API (`POST /api/recognize`), фото удаляются сразу после ответа, хранятся только цифры. On-device (WASM) — исследование: семисегментные экраны с бликами читаются ненадёжно. Распознанное всегда видно и правится человеком перед проверкой.
  - **Сделано в прототипе:** пачка фото → модель + 10 полей + уверенность + фото-источник у каждого поля; «визначити модель за фото» на экране выбора счётчика.
  - Тот же конвейер переиспользуем для **переноса бумажного журнала OTOS** (фото страницы → строки показаний) и позже для **платёжек** (фото/PDF → `bill_lines`).
