# Теплосервис — проверка показаний при вводе (v2, 01.11.2026)

## 1. Цель
Пока человек вводит показания (сайт, Mini App, бот) или они приходят по M-Bus, сразу видно: (1) нет ли ошибки; (2) примет ли ХТМ. Та же проверка — ещё раз перед фоновой отправкой. Окончательное «принято» даёт ответ ХТМ (verify), предпроверка убирает отказы заранее.

## 2. Вердикт — светофор
| | Значит | Действия |
|---|---|---|
| ✅ | Всё сходится, ХТМ примет | «Отправить» (уходит в фоне) / «Сохранить как промежуточное» |
| ⚠️ | Похоже на ошибку: поле, причина, что ожидали | Исправить или «Я перепроверил экран» (причина сохраняется) |
| ⛔ | ХТМ не примет: причина и что делать | Отправка заблокирована; можно сохранить как промежуточное |

## 3. Подсказка до ввода
«Энергия: ожидаем ≈ 15,9–16,3 Гкал» — от прошлого показания × среднесуточный расход с поправкой на градусо-сутки.

## 4. Проверки
**A. Формат** — маска разрядов, знаки после запятой, единица счётчика, запятая/точка; диапазоны модели (температуры 5…105 °C у Sharky 774; расход ≤ qs с запасом; мощность в физических пределах).

**B. История** — энергия, объём, часы On, Eh не меньше прошлых; прирост за сутки в пределах истории; ×10/×1000 → «запятая или единица»; **часы On ≈ календарь** (±24 ч); дата не в будущем и не раньше прошлой.

**C. Физика** — **мощность ≈ 1,163 × расход × (подача − обратка)** (кВт, м³/ч, K), допуск ±10 %; при расходе > 0 подача > обратки; расход 0 → мощность 0; за период ΔЭнергия/ΔОбъём (Гкал/м³ × 1000 ≈ средняя ΔT в K) в пределах ~1–30 K.
Проверено на журнале пользователя: расхождение 0,2–4,9 % на всех читаемых строках; восстановлены неразборчивые цифры: 03.11.25 обратка **43,56** (48,56 дало бы 0,04 кВт), 20.02.26 подача **56,57** (66,57 дало бы 19,2 кВт). Средняя ΔT по периодам — 3,1…12,7 K.

**D. Состояние счётчика** — код ошибки → объяснение из справочника; если тепло при этой ошибке не считается — ⚠️; рост Eh → ⚠️; батарея → ⚠️ + заказ замены; повирка просрочена → ⚠️ «ХТМ может не принять показания» (точное правило ХТМ не выяснено; не обещаем, что примут).

**E. Примет ли ХТМ** (`provider_rules`, `provider_windows`):
- отопительный сезон и окно: **тепло 5–25, рекомендовано до 23-го** (сайт ХТМ, 01.11.2026; договор 2021 говорил 23–26); ГВ онлайн — по предпоследний рабочий день месяца. До 23-го — ⚠️ «окно откроется 23-го, отправим автоматически»; после 26-го — ⛔ «окно закрыто, по договору начислят по среднему»;
- за период ещё не передавали;
- значение не меньше **последнего показания, числящегося в кабинете ХТМ** (читает адаптер); другое число в ХТМ (например, начислили по среднему) → ⚠️ с пояснением;
- формат и точность поля формы ХТМ (после снятия кабинета);
- доступ к кабинету работает; режим входа не отключён (после регистрации вход по счёту + фамилии не работает);
- счётчик найден в кабинете.

**F. Свежесть** — для отправки показание снято не раньше чем за 2 дня; если снято 23-го — пояснение, что ХТМ доначислит до конца месяца по среднесуточному.

## 4a. Правила робота ХТМ (памятка кабинета, снято 01.11.2026)
Полная таблица и коды `R_*` — документ «кабинет ХТМ (снятие 01.11.2026)», §7. Робот сравнивает с **предыдущей записью журнала** и проверяет период между датами: монотонность энергии, объёма, часов и часов с ошибкой; энергия выросла без объёма; средняя ΔT = ΔГкал·1000/Δм³ в пределах 2,5…50; средний расход ≥ 0,3 × переходного; температуры 5…95 и не 0; ΔT > 15 при неизменном объёме; |Δчасов − календарные часы| ≤ 24 (кроме приборов, считающих часы только при расходе: LQM-III ELF, ЛТЕ, TRUST, Ultrameter); прирост энергии < 15 Гкал; повирка не просрочена. Форма требует **все 10 значений** + телефон и email, разделитель — точка. Результат приходит через 15–30 минут в журнал — «принято» только после журнала.
Реализация: `web/src/rules.js` (тот же набор кодов будет портирован в PHP `Validator`).

## 5. Где работает
Один `Validator` (PHP) для всех входов: сайт/Mini App (проверка поля при вводе, API с задержкой ~300 мс), бот (после каждого шага + итог), M-Bus (молча, уведомление при ⚠️/⛔), перед фоновой отправкой (с актуальными данными из кабинета ХТМ).
```
Шаг 2/7 · Энергия, Гкал. Ожидаем ≈ 15,9–16,3
> 16,12
✓ +0,64 Гкал за 9 дней (0,071 в сутки) — как обычно
…
Итог: ✅ ХТМ примет (окно 5–25)
[Отправить] [Сохранить как промежуточное] [Исправить]
```

## 6. API и данные
```
POST /api/readings/validate
{ "meter_id": 12, "taken_at": "...", "fields": {"energy": 16.12, ...} }
→ { "verdict": "ok|warn|block", "items": [{"field":"power","level":"ok","code":"PHYS_POWER","msg":"...","expected":{"min":6.1,"max":7.5}}] }
```
```sql
CREATE TABLE provider_rules (
  id INT UNSIGNED AUTO_INCREMENT PRIMARY KEY, provider ENUM('htm') NOT NULL,
  kind ENUM('window','season','monotonic','precision','verification','registered','auth_mode','other') NOT NULL,
  params JSON, level ENUM('warn','block') NOT NULL,
  message_uk VARCHAR(255), message_ru VARCHAR(255), source VARCHAR(255), verified_at DATE NULL
);
CREATE TABLE provider_message_map (
  provider ENUM('htm') NOT NULL, pattern VARCHAR(255) NOT NULL, code VARCHAR(40) NOT NULL, PRIMARY KEY (provider, pattern)
);
CREATE TABLE validation_thresholds (`key` VARCHAR(60) PRIMARY KEY, value DECIMAL(12,4) NOT NULL, note VARCHAR(255));
-- окна приёма — provider_windows (главный документ)
```

## 7. Тесты
- Журнал пользователя — эталон: все читаемые строки ✅.
- Опечатки ловятся: 15,482 → 154,82; подача/обратка перепутаны; расход ×10; дата раньше прошлой; часы On не по календарю.
- Неразборчивые цифры восстанавливаются по формуле мощности.
- Правила ХТМ против стенда: 22-е (окно не открыто), 27-е (закрыто), значение меньше числящегося, повтор, режим входа отключён.
