# Промт для Claude в Chrome — снятие кабинета ХТМ и проверка автозаполнения (v2, 01.11.2026)

**Первая задача нового проекта.** Цель — убедиться, что сервис сможет в фоне сам войти в кабинет ХТМ, заполнить нужные поля и отправить показание, а пользователь в итоге только нажимает «Отправить» в сервисе и получает подтверждение «всё внесено». Claude в Chrome снимает структуру и проверяет, что поля находятся и заполняются; саму фоновую автоматику потом делает наш PHP-адаптер на NAS по результатам этого снятия.

**Когда запускать:**
1. **Сейчас** — этапы A, B, D (структура, вход, заполнение формы без отправки). Если вне окна форма закрыта — снимаем, как выглядит «закрыто» (это сценарий для стенда).
2. **23–26 ноября** (окно приёма тепла по договору ХТМ, п. 23) — этап C: одна настоящая отправка реального показания с записью запросов и подтверждения.

Владелец аккаунта ХТМ — пользователь, у него есть все права на свой кабинет. Вставить текст ниже целиком в Claude в Chrome.

---

Ты помогаешь собрать техническое описание личного кабинета КП «Харківські теплові мережі» (https://www.hts.kharkov.ua/cabinet/login) — моего собственного кабинета. По результатам мы соберём **локальный тестовый стенд** (копию логики кабинета для автотестов) и **адаптер**, который будет в фоне входить в мой кабинет, заполнять показания и отправлять их. Твоя задача — снять структуру и поведение страниц и проверить, что все нужные поля надёжно находятся и заполняются.

## Правила
1. **Логинюсь я сам.** Пароль, фамилию и лицевой счёт в чат не пишу и тебе не диктую — они не должны попасть в переписку. Когда нужен вход — скажи «войдите сами» и жди «готово». Сам сетевой запрос входа ты записываешь (значения маскируешь).
2. **Без моей команды ничего не отправляй и не меняй**: не передавай показания, не меняй email/пароль/настройки, не регистрируйся, не добавляй/удаляй квартиры.
3. **Заполнять поля формы можно** (этап D) — но **не нажимать «Відправити/Передати»**, пока я не напишу «отправляй».
4. Заведомо неверные значения (меньше прошлого, мусор) **не отправлять никогда**. Можно ввести их в поле без отправки, чтобы увидеть клиентскую проверку, и сразу очистить.
5. Ошибочный вход — максимум **одна** попытка и только по моему разрешению (снять текст ошибки). Никакого перебора.
6. Не вызывай alert/confirm/prompt; кнопки, которые могут открыть диалог, — только с предупреждением.
7. Только страницы из списка ниже, пауза пару секунд между переходами.
8. **Персональные данные вычищай** во всём, что сохраняешь или выводишь: ФИО → `{{SURNAME}}`/`{{NAME}}`, адрес → `{{ADDRESS}}`, лицевой счёт → `{{ACCOUNT}}`, email → `{{EMAIL}}`, телефон → `{{PHONE}}`, номер счётчика → `{{METER_SN}}`, суммы и показания — формат сохранить, цифры заменить (`13,245` → `99,999`), значения cookie и токенов → `{{TOKEN len=NN}}`. Имена полей, классы, id, URL-шаблоны, тексты интерфейса — как есть.
9. GIF не записывай (на экране персональные данные).

## A. Без входа
1. `/cabinet/login` — обе формы («Вхід за особовим рахунком», «Вхід за логіном та паролем»).
2. `/cabinet/register` и восстановление пароля — только посмотреть.

## B. Вход и навигация (вхожу я)
3. Перед моим входом включи запись сети (`read_network_requests`) в этой вкладке.
4. После «готово»: главная кабинета → список квартир/лицевых счетов → приборы квартиры (тепло, ГВ) → форма передачи показаний → история показаний → состояние счёта → настройки (структура) → выход (что с cookie).

## C. Настоящая отправка (только 23–26, только по моей команде)
5. Я пишу «отправляю» и нажимаю сам, **или** «отправь значение X» — тогда заполняешь и нажимаешь ты, один раз.
6. Запиши запросы, страницу подтверждения, затем открой историю — появилось ли показание, в каком виде.

## D. Проверка автозаполнения (без отправки)
7. На форме показаний найди для каждого поля **надёжный селектор** (id/name предпочтительнее CSS по классам): выбор прибора/квартиры, значение тепла, значение ГВ (если на той же форме), дата (если есть), поле для часов с ошибкой (если есть), кнопка отправки, скрытые поля.
8. Заполни поля тестовым значением через `form_input` / `javascript_tool` (значение «как прошлое», не отправляя), прочитай значения обратно из DOM, проверь, что форма считает их валидными (нет красных подсказок), сделай скриншот формы с замаскированными данными. Затем очисти поля.
9. Проверь: работает ли форма как обычный POST без JS (action, method, enctype, нет ли сборки запроса в JS); откуда берутся CSRF/скрытые токены и меняются ли они при каждой загрузке.

## Что записать для каждой страницы
- URL-шаблон, `<title>`, H1/H2, пункты меню.
- Каждая форма: `action`, `method`, `enctype`; поля — `name`, `type`, `id`, label/placeholder, `required`, `pattern`, `maxlength`, `min/max/step`, значение по умолчанию; все hidden-поля (имя + формат значения); кнопки.
- Формат ввода показания: разделитель, знаков после запятой, единица, поле даты, выбор прибора.
- Клиентская валидация (что проверяют скрипты), подключаемые JS-файлы (имена).
- Тексты всех сообщений дословно (успех, ошибки, «прийом показань закрито», «показання менші за попередні» и т.п.), даты окна приёма, если где-то написаны.
- Признаки защиты: капча, 2FA, rate-limit, проверка User-Agent/Referer.

## Сеть (вход, переход к форме, отправка, выход)
Метод, URL, статус, редиректы (`Location`), `Content-Type`, XHR или обычный POST, имена полей тела (значения маскировать), имена cookie и атрибуты (`HttpOnly`, `Secure`, `SameSite`, срок) **без значений**, откуда CSRF.
